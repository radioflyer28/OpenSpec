## Context

See [proposal.md](./proposal.md) for motivation. The maintained fork currently identifies itself as `1.8.0-gsd.1` and carries a generic extension/workflow/archive-gate seam plus its tests, documentation, packaging metadata, and upstream-survivability tooling. OpenSpec GSD remains a companion package; its orchestration and agent-role behavior must not move into OpenSpec core.

The upgrade crosses the upstream 1.9, 1.10, and 1.11 releases. Some upstream changes overlap CLI registration, archive behavior, generated workflow handling, package metadata, tests, and lockfiles—the same areas touched by the seam. The working checkout also contains unrelated local work, so rewriting it in place would create unnecessary recovery risk.

The release baseline is the immutable official `v1.11.0` tag. The moving `upstream/main` ref is useful only for detecting likely future conflicts. Local acceptance targets macOS, while the existing automated OpenSpec test matrix remains responsible for inherited cross-platform behavior.

## Goals / Non-Goals

**Goals:**

- Reconstruct the smallest viable OpenSpec extension seam on a clean `v1.11.0` base without losing upstream behavior.
- Produce a traceable private fork build identified as `1.11.0-gsd.1`.
- Prove that OpenSpec GSD's current manifest, workflows, Pi adapter, assurance records, and archive gates work with the upgraded base.
- Preserve a repeatable patch-and-qualification path for later upstream releases.
- Make installation reversible until the new CLI and companion package pass an installed-system smoke test.

**Non-Goals:**

- Changing OpenSpec GSD requirements, workflows, prompts, assurance policy, or generated record formats.
- Moving companion orchestration into OpenSpec core.
- Publishing either package to npm or creating a public OpenSpec release.
- Basing the private build on unreleased `upstream/main` commits.
- Manually qualifying additional operating systems; platform coverage is limited to existing automated CI.

## Decisions

### 1. Reconstruct from the official tag in an isolated worktree

Create a dedicated integration branch and worktree from the verified upstream `v1.11.0` tag, then apply the allowlisted seam there. Preserve the current branch and dirty working tree untouched until the integration result is ready to merge.

This produces a reviewable history whose base is unambiguous and avoids mixing a three-release upstream update with unrelated local edits. A direct in-place rebase was rejected because it expands conflict and rollback risk. Merging the entire current fork branch into `v1.11.0` was rejected because it makes it harder to distinguish the generic seam from accumulated project history.

### 2. Treat deterministic seam metadata as the migration recipe

Generate the carried patch from the configured extension-seam allowlist and its recorded upstream base. Apply source, tests, documentation, and package-export changes as one bounded seam, then resolve overlapping files in favor of upstream 1.11 behavior unless the extension contract requires a deliberate hook.

Update the seam budget and survivability configuration to name the new base and every intentionally carried path. Any changed path outside that declaration requires explicit review and either inclusion with rationale or removal. Copying files ad hoc was rejected because it would make later upgrades irreproducible.

### 3. Preserve behavior through tests, not by preserving old file bodies

For overlapping files, first retain upstream 1.11 implementations and reintroduce only the narrow discovery, reconciliation, workflow, and archive-gate calls needed by the public extension API. Existing extension tests and the companion conformance suite define the carried contract; old implementation text does not.

This reduces accidental rollback of upstream fixes. Blind three-way conflict resolution in favor of either side was rejected because both upstream behavior and seam behavior are required.

### 4. Keep core and companion compatibility explicit

Set the fork package version to `1.11.0-gsd.1`. Update the companion's development/test baseline and compatibility documentation so the qualified pairing is explicit. The companion may keep a bounded semver range only if installation and startup also verify that the OpenSpec extension API is actually present; official `1.11.0` alone is not equivalent to the patched build.

No OpenSpec GSD feature version bump is required unless companion source or its public package contract changes during compatibility remediation. Generated artifacts may be regenerated by the new CLI, but unexpected semantic diffs are blockers rather than automatic migrations.

### 5. Use layered qualification with fail-fast boundaries

Qualification proceeds in this order:

1. Verify the tag, package version, Node/pnpm prerequisites, seam source base, and clean isolated target.
2. Build and run OpenSpec lint, full tests, focused extension/archive/workflow tests, package checks, and seam-budget checks.
3. Apply the rebuilt seam to current `upstream/main` in prepare-only mode to detect forward conflicts; failure blocks completion, while success does not change the release base.
4. Pack the patched CLI without publishing it, install the artifact in an isolated prefix, and verify its version, exports, lifecycle commands, workflow generation, and archive gates.
5. Install/test the companion against that exact packed CLI, run its full tests and conformance suite, and exercise the Pi adapter on macOS.
6. Replace the user's installed build only after isolated qualification passes, then run one new-project end-to-end smoke test including a blocking and passing archive-gate path.

This sequence localizes failures and prevents a partially qualified global installation. Running only focused seam tests was rejected because upstream integration can fail outside the seam. Running only the full OpenSpec suite was rejected because it does not establish companion or installed-host behavior.

### 6. Make installation private and reversible

Retain the previously working `1.8.0-gsd.1` package artifact or an exact reproducible Git ref before changing the installed CLI. Record the newly packed artifact's checksum and install OpenSpec before linking/installing OpenSpec GSD. Do not invoke npm publication, release, changeset-publish, or registry mutation commands.

If installed qualification fails, restore the prior CLI/package pairing and keep the failed integration branch and evidence for diagnosis. This is preferable to repairing directly in the global installation, which would make the tested artifact differ from the developed artifact.

### 7. Keep execution evidence subordinate to OpenSpec artifacts

The change's proposal, design, and tasks remain the human-maintained planning truth. Test logs, patch reports, packed-artifact metadata, and compatibility results may be recorded as generated evidence, but they do not introduce GSD milestones, phases, roadmaps, or parallel planning state.

## Risks / Trade-offs

- **[Upstream overlaps change behavior while the seam still compiles]** → Resolve overlaps from the upstream implementation outward, then run both upstream and extension-specific behavioral suites.
- **[The allowlist omits a necessary carried file or includes unrelated history]** → Inspect the generated patch and seam-budget report before applying it; require a rationale for every added path.
- **[A broad companion peer range accepts official OpenSpec without the seam]** → Pair semver checks with extension-API capability detection and document the qualified patched baseline.
- **[Generated workflow reconciliation modifies user-owned files]** → Exercise conflict, recovery, idempotency, replacement, and ownership-marker cases before system installation.
- **[The moving upstream branch fails after the stable build passes]** → Treat this as forward-maintenance work that blocks declaring the seam survivable, not as permission to include unreleased code in the build.
- **[Local macOS success conceals a platform regression]** → Require the existing automated Linux/macOS/Windows OpenSpec matrix where available; do not require manual machines for this private installation.
- **[Global installation interrupts the current working setup]** → Qualify packed artifacts in isolation, retain the prior pairing, and perform the global replacement last.
- **[Private version metadata accidentally enters a publication path]** → Use pack/install commands only and audit command configuration and logs for registry-mutating operations.

## Migration Plan

1. Capture the current fork, companion, installed CLI, Pi, and extension-lock state, including exact revisions and versions.
2. Verify and fetch the official `v1.11.0` tag, then create an isolated integration worktree and branch from it.
3. Generate, inspect, and apply the minimal seam; resolve overlaps and update the version, lockfile, seam budget, and survivability metadata.
4. Run core and forward-survivability qualification. Stop without changing the installed system if any required check fails.
5. Update and qualify the companion against the packed `1.11.0-gsd.1` artifact. Keep compatibility-only edits separate from feature work.
6. Pack both projects as needed, record checksums and test results, and install/link them in an isolated environment for Pi and archive-gate smoke tests.
7. Preserve rollback inputs, replace the user's installed OpenSpec and OpenSpec GSD pairing, and repeat the new-project smoke test.
8. Merge the bounded integration commits only after all required checks pass. Keep any unrelated working-tree changes outside those commits.

Rollback restores the recorded `1.8.0-gsd.1` CLI and previously qualified companion link/package, then verifies `openspec --version`, extension discovery, and project doctor output. The failed `1.11.0-gsd.1` integration remains available for repair without becoming the active installation.
